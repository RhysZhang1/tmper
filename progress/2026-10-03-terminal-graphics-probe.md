# 2026-10-03 会话（续二）：终端图形能力探测，以及 Kitty 载荷的三个真 bug

> 问题 3（Konsole 之外的兼容性）的落地。上一轮（`2026-10-03-encoder-and-terminal-compat.md`）
> 查明了两件事：tmper 只有 SIXEL 有探测，Kitty 路径只看环境变量；而 **Konsole 26.08 其实
> 实现 Kitty 图形协议，却一个相关环境变量都不设**——环境变量判据天然认不出用户自己的终端。
> 本文记录这一轮的改动与实测。

## 一、启动探测（`probe_terminal_once`）

一趟写完、一趟读回，共四个问题：

```
CSI 16 t                                        单元格像素
CSI 14 t  +  CSI 18 t                           文本区像素（只有这两个的终端，相除同解）
ESC _ G i=31,s=1,v=1,a=q,t=d,f=24;AAAA ESC \    Kitty 图形协议自己的能力查询
CSI c                                           DA1，同时充当屏障
```

- **DA1 放最后**：回复按发送顺序到达，而每个终端都会答 DA1。所以「DA1 完整到达」就等于
  「前面问的都已经到了」，不必等满超时。
- **APC 查询是安全的**：不实现该协议的终端整段忽略（不画、不答）；实现的终端答
  `ESC _ G i=31;OK ESC \`。Konsole 26.08 实测如此。
- **用 `poll(2)` 而不是读**：探测期不消费输入队列，超时（80 ms）只对「从不回答的终端」
  收费。迟到的回复落到输入线程也不会变成按键：crossterm 把 `CSI ? … c` 映射成
  `InternalEvent::PrimaryDeviceAttributes`，没有对应的公开 `Event`。
- **多路复用器**（`TMUX`/`STY`/`ZELLIJ`）：识别到就**不问图形问题、也不采信图形回答**，
  一律半块字符。理由见第五节。

## 二、Kitty 载荷的三个真 bug（症状都是「封面面板空白」）

三个都是**单元测试全绿**、把 tmper 的真实字节流抓下来回放进真 Konsole 才暴露的。它们的
共同点是：载荷看起来完全正常，终端却一个字都不说地丢掉。

### 1. `p=330,360` —— 位置填进了 it 的 id 槽

协议里 `p` 是 **placement id**，不是像素坐标。tmper 把封面的像素偏移塞进 `p`，Konsole
校验这个参数后**整张图丢弃**。改法：去掉 `p`，用 `CSI <row>;<col> H` 把光标移到封面矩形
再发（SIXEL 路径本来就是这么定位的）。变体实验（同一张图，只改这一个参数）里，只有带
`p=` 的那一版不显示。

### 2. 分块传成了 88 张残图

协议要求**只有第一块**带完整命令头，后续块只能是 `ESC _ G m=<more>;<data> ESC \`。
tmper 每一块都重复 `a=T,f=100,s=…,v=…,c=…,r=…`，于是每一块都被当成一张独立的、被截断
的图。Konsole 对每一张回 `ENOENT: No such image`，**而那条 APC 回复落在 stdin 上被读成
按键**——在真实终端里表现为命令模式里多出一串 `_Gi=0;ENOENT:No such image`。

### 3. 头说 `f=100`（PNG），发的却是裸 RGB

`to_rgb8().into_raw()` 给出 208×210×3 = 131040 字节：尺寸对、像素对、**格式不对**。
终端按 `f=100` 选 PNG 解码器，解不开就静默丢弃——而 `q=2` 把错误回复也关掉了，于是
「什么都不发生」。改法：用 `image::codecs::png::PngEncoder` 编成真正的 PNG。顺带收益：
同一张封面 131040 → 11751 字节，分块数 44 → 4。

### 附带一条规则：`q=2`

所有图形命令都带 `q=2`（不回复）。任何错误回复都是 APC 字节，落在 stdin 上会被读成按键
——这正是历史上「幽灵按键」的同一类问题，`2026-08-03-cover-refactor.md` 里打过一次。

## 三、怎么验证的（可复现）

单元测试看不见这一层：它只能断言「字节发对了」，断言不了「终端接受了」。

1. **抓流**（`/tmp/capture_keys.py`）：在 pty 里跑 tmper，按 Konsole 的方式回答启动探测，
   可注入按键，把 tmper 写出的**全部字节**存下来。
2. **回放**（`/tmp/replay_stream.py`）：把这份字节流原样写进一个**真 Konsole** 窗口，截图。
3. **判据**：回放能看到封面 = 载荷本身被 Konsole 接受，问题在别处；看不到 = 载荷被拒。
   这次是后者，才顺着抓下来的字节找到了上面三个 bug（第二个 bug 甚至能从流里直接读出来：
   44 个分块、44 个命令头）。

## 四、实测结果（Konsole 26.08 / KDE Plasma 6 / Wayland，单元格 8×15 px）

| 场景 | 结果 |
|------|------|
| 启动 | 封面出现在 Now Playing 面板；无幽灵按键；面板几何与半块字符图层一致 |
| `2` 切到曲库 | 封面清除干净，曲库视图无残留（`ESC _ G a=d,d=I ESC \` 在 Konsole 上有效） |
| `1` 切回播放器 | 封面重新出现（`clear_kitty` 一并清掉「已放置」记录，因此必定重发） |
| 整个会话 | 两次传输（放置 → 字符画让位那一帧被改写 → 重发），之后不再重发 |

## 五、能力链（现在的选择顺序）

```
Kitty（终端回答了 a=q）
  → SIXEL（DA1 含属性 4）
    → 半块字符
多路复用器 → 直接半块字符
```

- DA1 的属性按**数值**匹配，「24」不会被当成「4」。
- 为什么 Kitty 优先：真彩 vs 256 色寄存器，封面是照片，色带差别看得见。
- 为什么多路复用器一律退字符画：tmux/screen/zellij 默认**吞掉** DCS/APC 载荷，而它们的
  查询回答**可能仍来自底下的真终端**——「回答支持、载荷被吞」正是空白面板的组合。开启
  passthrough 需要 tmux 3.4+ 且 `allow-passthrough on`，属于用户侧配置，探测不到；发错了
  的代价是花屏或空白，比字符画差得多。所以这一轮**不做** passthrough，直接退字符画。

## 六、没做的

- tmux/screen/zellij 的 passthrough 包装（理由见上）。
- MPRIS（问题 2）：按用户要求暂缓，等兼容性这一轮结束后再单独开工。

```bash

# 回放进真 Konsole 并截图
/tmp/replay_shot.sh /tmp/stream.bin /tmp/shot.png
# 只看 Kitty 事务本身
python3 /tmp/kitty_extract.py     # 分块数、载荷格式、PNG 尺寸
```
